## 2. v1 実装前に確認しておくとよいポイント

### 2-1. OAuth フローまわり（state / セッション前提）

**どこかに書いてあれば OK ですが、文書には明示されてなかったので念のため。**

* `connect` → Google 同意 → `callback` の間で
  **「誰の接続か」をどう紐づけるか**をちゃんと決めておくと安全です。

特に：

1. **`state` パラメータを必ず使う**

   * ランダムトークン or 暗号化した `user_id` を `state` に載せる。
   * `callback` で `state` を検証しないと、CSRF 的に「別ユーザーのセッションでトークンが紐づく」事故があり得る。

2. **Callback 時に Supabase セッションがなくても良い設計にするか**

   * パターンA: 「ログイン中の人だけ設定画面から `connect` を叩ける」運用にして、`callback` 時も必ず Supabase セッションがある前提にする。
   * パターンB: `state` に `user_id` を暗号化して入れておき、`callback` 側は Supabase セッションに依存しない（`state` から user を特定）。

どっちでもいいですが、どちらかに **方針を固定しておく**と実装がブレません。

---

### 2-2. refresh_token が取れない／消えるケースの扱い

仕様どおり書いても、Google OAuth あるあるで：

* 2回目以降の同意では `refresh_token` が返ってこない
* ユーザーが Google 側で権限を取り消した
* しばらく使ってなくて refresh_token が無効化された

みたいなパターンが出ます。

最低限、v1 で意識しておくと良いのは：

* `google_calendar_accounts.scope` と `token_expires_at` を信用し過ぎない
* Calendar API 呼び出し時に 401/403 が返ってきたら

  * DB のトークンをクリア
  * フロントに「連携が無効になったので再接続してください」の状態を返す

という **“壊れた連携をどう扱うか” の決め方**です。
ここが決まっていると、v2/v3 でも同じパターンが使い回せます。

---

### 2-3. callback / events API でのログ出力の線引き

v1 から最低限決めておきたいのがこれ。

* **絶対にログに書かないもの**

  * `access_token`
  * `refresh_token`
* なるべく抑えたいもの

  * 生のイベント内容（タイトル・メモ）
  * 生のレスポンス JSON 丸ごと

開発中は `console.log(res.data)` とか書きがちですが、
本番でもそのまま出ると PII ガンガン吐くので、

* envで `LOG_LEVEL=debug` のときだけ詳細に出す
* 本番ログには event の `id` と `status` くらいまで

みたいなラインを決めておくとあとで楽です。

---

### 2-4. `/api/calendar/events` の API 仕様を固定する

v2/v3 で拡張しやすくするために、v1 のうちに API の形をある程度固めておくと良さそうです。

例えば：

* クエリ:

  * `start` / `end` は ISO8601 で固定（`start` 必須, `end` 省略時は start + 7日 などでも可）
* レスポンス:

  * **Taesk 用の軽量な型に変換して返す**

    * `id`
    * `title`
    * `start`
    * `end`
    * `isAllDay`
    * `source: "google_calendar"`
  * Google の生データをそのまま返さない（後で差し替えしやすくする）

v2 で Taesk カードも同じタイムラインに載せるとき、
ここがきれいだとかなり扱いやすいです。

---

### 2-5. タイムゾーンと終日イベントの扱い

v1 時点で最低限決めておきたいのは：

* `timeZone` をどう解釈するか

  * ユーザーのプロファイルにタイムゾーンを持つのか
  * ひとまず JST 固定なのか
* `date`（終日）と `dateTime`（時間あり）の両方への対応

  * `date` だけのイベントは「0時〜24時扱い」にするのか
  * Timeline 上の描画ルール（終日は上部に1行で出す etc）

ここを考えずに突っ込むと、
後で「なぜか1日ずれる」「終日イベントが変な位置に出る」みたいな細かいバグが出やすいです。

## 3. v2 / v3 を見据えて、v1で決めておくと後が楽なこと

v1 は読み取りだけですが、「今のうちに頭の片隅に置いておくと v2/v3 が楽」というポイントをいくつか。

### 3-1. カレンダーIDの扱い（今は primary 固定か、それとも拡張を意識するか）

v1 では `primary` 固定で全然いいのですが、

* `GET /api/calendar/events` の内部実装では `calendarId = "primary"` をハードコードしつつ、
* DBスキーマや型には `calendar_id` を入れておく余地を残しておく

と、

* v2 で「このカレンダーだけ書き込みたい」
* v3 で「複数カレンダーを監視」

にするときに差分が最小で済みます。

今の設計に「カレンダー指定」の考え方はすでに書かれているので、
**実装として `calendarId` を 1引数にしておく**ぐらいで十分です。

---

### 3-2. `calendar_sync` / `extendedProperties` 用の命名方針だけ決めておく

v2で使う前提の `calendar_sync` は、v1ではテーブルを作らなくてもいいですが、

* 「Taesk が Google イベントに書き込むときは、
  `extendedProperties.private.taeskCardId` を必ず入れる」
* 「他サービスと衝突しないよう prefix つける（例: `taesk:cardId`）」

みたいな**命名規則だけ先に決めておく**と、
後から仕様書くときに迷いません。

v1 のコード中にコメントで

```ts
// v2以降: Googleイベント extendedProperties.private["taeskCardId"] にカードIDを入れる
```

みたいに書いておくのがおすすめです。

---

### 3-3. 「同期対象カードの絞り方」を頭の片隅に

v2 では「カードごとに opt-in（連携するカードだけ Google に出す）」構想でしたよね。カード単位で `sync_enabled` を持たせて、ON のカードだけ `calendar_sync` に紐付け・イベント作成/更新/削除するのが方針。

それに合わせて、

* v1 の時点で Timeline 側のデータモデルに

  * 「外部連携系のフラグを載せる領域」を今から確保しておく
* UI 的にも

  * 「カードを右クリック → ‘Googleカレンダーに出す’ チェック」
  * みたいな未来像を頭にいれてレイアウトを組んでおく

くらいをやっておくと、後で UI をガラッと変えずに済みます。

### 3-4. Webhook (v3) で拾える範囲の理解

`events.watch` は **カレンダー単位の変更通知** しか来ないので、特定イベントだけをピンポイント購読することはできません。通知を受けたら `syncToken` 付き `events.list` で差分を取得し、どのイベントが変わったかを判定する流れになります（自分が直前に書いた変更かどうかは `extendedProperties` などで判定）。
