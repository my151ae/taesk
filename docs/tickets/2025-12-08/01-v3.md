## 0. 用語と状態

### 0.1 カード種別とシンク状態

内部的なレコード種別は **GCard / TCard の 2 種のみ**とし、  
UI/仕様上は **「GCard / TCard(SyncOff) / TCard(SyncOn)」の 3 区分**で説明する。

- **GCard（Googleカード）**  
  - Google カレンダー由来のイベントを Taesk 側に**キャッシュしたレコード**。  
  - デフォルト状態では **未シンク（Google のみがソース）**。  
  - Google から取得したタイミングで必ず DB に保存し、以後は DB から即座に表示する。  
    - 変更検知（push / pull）で差分を受信したときのみ GCard を更新する。

- **TCard（Taeskカード）**  
  - Taesk 内で作成されたローカル専用カード。  
  - 一度 TCard(SyncOn) だったものがシンク解除された後のカードも、この TCard に含めて扱う。  
  - 「Googleとシンク」チェックが OFF の状態を **TCard(SyncOff)** と呼ぶ。

- **TCard(SyncOn)（= Google接続 Taeskカード）**  
  - 「GCard と 1:1 で接続されている TCard」を指す**シンク状態**。  
  - 実体としては TCard レコードであり、別途 GCard レコードとシンク情報を持つ。  
  - Taesk と Google の**双方向自動同期**が有効。  
  - UI 上のバッジ名は「Google接続」とし、内部状態名を TCard(SyncOn) とする。

> 以降は混乱を避けるため、  
> - レコード種別: **GCard / TCard**  
> - TCard の状態: **TCard(SyncOff) / TCard(SyncOn)**  
> の 2 層構造で用語を統一する。

### 0.2 終日 / 日付だけタスクの用語

- **終日イベント（All-day）**  
  - Google カレンダー上で `date` 型の `start` / `end` を持つイベント。  
  - Taesk 上では「終日 TCard(SyncOn)」として扱う。

- **日付だけタスク**  
  - Taesk の A/B リスト上に存在する、**時間未設定の TCard(SyncOff) / TCard(SyncOn)**。  
  - Taesk 上では従来通りリストのカードとして表示し、カレンダー帯状 UI にはしない。  

- **終日 TCard(SyncOn) の表示方針**  
  - Google 側では **終日イベント（帯状表示）** として扱う。  
  - Taesk 側では **A/B リスト上のカードとして表示**し、帯状 UI にはしない。  
  - 終日イベントのローカル日付は、Google カレンダーと **必ず一致するローカル日付**になるよう  
    `date` + `display_tz` を用いて解釈する（→ 1.5, 4. 参照）。
  - GCard 終日イベントをシンク ON して TCard(SyncOn) に変換した場合、カレンダー帯状 UI からは消え、A/B リスト上の「終日 TCard(SyncOn)」としてのみ表示される。  

### 0.3 状態遷移（概要）

- **GCard →（「Googleとシンク」ON）→ TCard(SyncOn)**  
  - 既存 Google イベントを起点に **Taesk 側の TCard レコードを生成**し、1:1 接続して双方向同期を開始。  
  - **候補 UI なしで即接続**する。  
  - シンク成立後、当該 GCard は UI からは単体カードとしては表示せず、  
    対応する **TCard(SyncOn)** のみがユーザーの操作対象となる。

- **TCard(SyncOff) →（ON）→ Google へ新規イベント作成 → TCard(SyncOn)**  
  - チェック ON で、**必ず Google に新規イベントを作成**する。  
  - 既存イベントとの候補照合や近似マッチは行わない。  
  - 作成された Google イベント ID を保持し、TCard は TCard(SyncOn) 状態になる。

- **シンク解除済み TCard →（ON）→ TCard(SyncOn)（再シンク）**  
  - 一度 Google とシンクしていたが、ユーザー操作や削除等で切断された TCard。  
  - この状態のカードでチェック ON した場合のみ、**近似マッチ候補 UI** を表示する。  
  - 既存 Google イベントに再接続するか、「新規作成」を選択して新しいイベントを作る。

- **TCard(SyncOn) →（OFF）→ TCard(SyncOff)**  
  - 「Googleとシンク」チェックを OFF にした場合はいつでも接続解除でき、  
    カードはローカル専用の TCard(SyncOff) として残る（Google 側のイベントは削除しない）。

## 1. 仕様（決定事項）

### 1.1 シンク管理（チェックボックス運用）

- カード詳細に **「Googleとシンク」** チェックボックスを設置（既定 **OFF**）。  
- ON 中は TCard(SyncOn) として**双方向自動同期**。OFF でローカル専用の TCard(SyncOff)。  
- **自動 OFF のルール**  
  - 原則、Taesk 側から自動で OFF（Unsync）にはしない。  
  - ただし、以下の場合は例外として自動 Unsync する：  
    - Google 側で `status=cancelled` または削除された場合（→ 1.11）  
    - 認可エラー（`invalid_grant` 等）でユーザー同意が完全に失われた場合（→ 1.9）  

### 1.2 シンク/再シンク時の挙動

#### GCard → TCard(SyncOn)

- 「Googleとシンク」ON で **候補 UI なし**に、その Google イベントへ即接続。  
- このとき GCard を起点に **対応する TCard を新規作成**し、1:1 でシンクする。  
- シンク成立後は、**TCard(SyncOn) を編集の主体**とし、  
  当該 GCard は UI 上では単独カードとしては表示しない（内部的なキャッシュとしてのみ保持）。

#### TCard(SyncOff) → TCard(SyncOn)（新規作成）

- チェック ON で **常に Google へ新規イベントを作成**する。  
  - 既存 Google イベントを候補として提示したり、近似マッチで自動接続したりはしない。  
- 作成された Google イベント ID を保持し、TCard は TCard(SyncOn) 状態になる。

#### シンク解除済み TCard → TCard(SyncOn)（再シンク）

- 「以前は Google とシンクしていたが、現在は OFF（未接続）」という TCard。  
- この状態のカードでチェック ON した場合のみ、**近似マッチ候補 UI** を表示する。  
- 既存 Google イベントに再接続するか、「新規作成」を選択して新しいイベントを作る。

#### 近似マッチスコア（再シンク時専用）

- 指標: **タイトル文字列の Jaro-Winkler 類似度**（1.0 が完全一致）。  
- しきい値: **0.75 以上**を候補として掲出する。  
- 時刻や場所はスコア計算に含めず、**タイトルのみで判定**する。  
- `status=cancelled` のイベントも、他と同様に候補に含める（除外しない）。  
- 自動確定は行わず、必ずユーザーの選択を挟む。  
- 候補 0 件の場合の UX（デフォルトで「新規作成」を選ぶか、明示選択を必須にするか）は実装側で一意に決める。

### 1.3 同期対象（白リスト）

#### Taesk ↔ Google の往復同期対象

- タイトル
- 説明
- 場所
- 開始日時・終了日時
- 終日フラグ（`date` / `dateTime` + `timeZone`）

#### Google → Taesk のみ同期（Taesk 側は編集不可）

- **会議 URL**  
  - Google 側の `conferenceData`（および説明欄に含まれる URL）を読み取り、Taesk 上の「会議 URL」フィールドに表示する。  
  - Taesk では **会議 URL フィールドは編集不可** とし、ここでの変更は Google に書き戻さない。  
  - Google 側で会議情報が更新された場合は、Push / Poll により Taesk 側表示が上書きされる。

#### Taesk 専有（Google とは同期しない）

- ラベル
- チェックリスト / サブタスク
- 担当者
- 内部コメント
- カスタムフィールド
- **完了/未完了ステータス・その他ステータス**

> TCard(SyncOn) を「完了」にしても Google カレンダー側には何も送られない。  
> Google に「完了」の概念を持ち込まず、タスク管理は Taesk 側で完結させる。

### 1.4 繰り返し/例外

- Google API では `singleEvents=true` でインスタンス展開。  
- 展開ウィンドウ: **過去 4 週 / 未来 12 週** を基本とする（画面スクロール等に応じて段階的にプリフェッチ）。  
- 例外インスタンスは `recurringEventId` + `originalStartTime` を保持し、**常に個別インスタンスとして扱う**。

#### Taesk 側からの編集粒度

- Taesk から TCard(SyncOn)（繰り返しイベント）を編集する場合、**当面は「このインスタンスのみ」編集**とする。  
  - Google API に対しても、シリーズ全体ではなく該当インスタンスへの変更として送信する。  
  - 「シリーズ全体を変更」する UI や機能は提供しない。  
- Google 側で「シリーズ全体」を編集した場合は、`singleEvents=true` による展開結果として  
  Taesk 側に反映される（Taesk 側で特別扱いはしない）。

### 1.5 終日（All-day）・日付だけタスク

- **GCard の終日イベント**  
  - Google カレンダーと同じ内部表現（`date` / `display_tz` / `start_utc` / `end_utc`）を採用。  
  - Taesk カレンダー上では、ヘッダー直下に帯状 UI で表示する。  
- **終日 TCard(SyncOn) の扱い**  
  - Taesk から「終日」として作成/編集された TCard(SyncOn) も、Google 側では All-day イベントとして保存する。  
  - Taesk 側では **A/B リスト上のカードとして表示**し、帯状 UI は用いない。  
- **日付だけタスク（時間未設定 TCard(SyncOff) / TCard(SyncOn)）**  
  - Taesk 側の「日付だけタスク」は、終日帯状 UI にはしない。  
  - 引き続き A/B リスト上のカードとして扱う。  
- **ローカル日付の一致**  
  - 終日イベントのローカル日付は、Google カレンダーで見える日付と **常に一致**することを保証する。  
  - そのために `display_tz` を「解釈の基準 TZ」として保持し、  
    DST / TZ 跨ぎを含めて `date` 範囲を正しく解釈する（→ 4. も参照）。

### 1.6 同期方式・競合・冪等性

- TCard(SyncOn) 中は **双方向自動同期** を行う。  
- Google 更新時は `If-Match` を利用し、競合が発生した場合は **更新時刻が新しい側** を採用。  
- **自己更新スキップ**  
  - Taesk 自身が直前に書き込んだ変更（`etag` / `updated` 等）を取り込みパイプで検出し、  
    それに起因する更新を無視することで、更新ループを防ぐ。  

#### 冪等キー

- TCard から Google へ新規作成する際、`extendedProperties.private.idempotency_key` による **冪等キー** で多重作成を防止する。  
- キーの例: `taesk:{tcard_id}:{created_at_iso}`。  
- **保持ポリシー**  
  - 少なくとも **24 時間** は同一キーでの重複作成を拒否する。  
  - 実装では 7 日程度まで保持していてもよいが、ストレージ負荷とのバランスで調整可能とする。

### 1.7 取り込み/通知（Push + フォールバック）

- 初回はフル取得 → 以降は `syncToken` による差分運用。  
- `showDeleted=true` を指定し、キャンセル/削除イベントも取得する。  

#### Push（watch）主体

- `channels.watch` / `channels.stop` を用いて、**Push を主体**とする。  
- watch の単位は **「Taesk ユーザー × Google カレンダーID」** とする。  
  - 1 ユーザーが同一カレンダーを複数ビューで利用していても、watch は 1 本にまとめる。  
  - 複数ユーザーが共有カレンダーを使っている場合、それぞれの Google アカウントごとに watch が存在し得る。  

- 寿命 30% 前の watch 再作成  
  - Google が返す有効期限を基準に、残存寿命が 30% を切ったタイミングで再作成する。  
  - 「寿命 30% 前」というしきい値は、メトリクスから変更可能とする（→ 5.）。

#### 動的フォールバック

- 無更新しきい値 = **p95 取り込み遅延 × 3**。  
  - p95 は「直近 24 時間の、当該カレンダーに対する Push 経路の取り込み遅延分布」に基づき、  
    **カレンダー単位（= watch 単位）で計測**する。  
- しきい値を超えて更新が一切来ない場合、そのカレンダーに対しては一時的に **ポーリングに切り替え**る。  
- 後続のポーリング / Push により正常な更新が観測されたら、自動でポーリングを停止し、Push を再有効化する。

#### `410`（syncToken 無効）時の挙動

- `410 Gone` を受け取った場合は、**透過的にフル再同期**する。  
- 再同期中:
  - ユーザーには直前までのキャッシュ内容を表示し続ける。  
  - 明示的なエラー表示は行わず、必要に応じて「同期中」インジケータのみ表示する。  
- 再同期が完了すると、最新状態で UI を更新する。  
  - このケースは「異常」ではなく、「許容される再同期」として扱い、  
    「同期エラー」バッジの対象にはしない。

### 1.8 UI/UX

- バッジ  
- GCard = 「Google（未シンク）」  
  - TCard(SyncOn) = 「Google接続」  
  - TCard(SyncOff) = 「未接続」  
  - エラー = 「同期エラー」
- **同期エラー バッジ付与/解除条件**  
  - 同一 TCard(SyncOn) に対する Google API 呼び出しが、**3 回連続で失敗**した場合に付与する。  
    - 対象となる失敗: `429 / 5xx`、その他一時的な失敗。  
    - 認可エラー（`401/403`）は 1.9 のルールに従い、別途扱う。  
  - その後、同カードに対する同期が 1 回でも成功したら、自動でバッジを解除する。  

- **今すぐ同期**  
  - 詳細パネルに常設（手動リトライ / 即時反映用）。  
  - 保存直後は **「同期中 → 同期完了」** のスナックバーを表示。

- 参加者 / RSVP  
  - 表示のみ（編集不可）。  
  - 5 名を超える場合は “+n” で省略表示。

### 1.9 セキュリティ/権限

- オンボーディング時に、全ユーザーへ `…/calendar.events` スコープを要求（双方向同期を前提とした権限設計）。  
- トークン失効時の扱い:
  - 一時的なネットワークエラーや 5xx の場合は、指数バックオフで再試行しつつ「同期エラー」バッジで通知。  
  - `invalid_grant` などにより、**ユーザーの同意が失われたことが明白**な場合:
    - 当該ユーザーの全 TCard(SyncOn) を **TCard(SyncOff) に自動降格**し、  
      「Googleとシンク」チェックも OFF にする。  
    - 画面上には「再接続」導線を固定配置し、ユーザーが再度連携を有効化できるようにする。

### 1.10 観測性/SLO

- 記録する主なメトリクス  
  - **E2E 取り込み遅延**: `t_change（Google 側変更） → t_visible（Taesk 画面で最新状態が取得可能になった時刻）`  
  - **システム内部遅延**: `t_ingress（Webhook/ポーリング受信） → t_visible`  

> `t_visible` は「フロントエンドが次回 API コールを行ったときに、  
>  すでに最新状態を取得できるようになっている時刻」と定義する。  
> DOM 更新完了時刻ではなく、API レイヤーの完了を基準にする。

- SLO（例）  
  - Push 経路の **p95(E2E) ≤ 60 秒**。  

- アラート条件（例）  
  - Push 経路の p95(E2E) ≥ 60s が 5 分以上継続。  
  - 有効な watch の残存寿命 < 30% なのに再作成されていない。  
  - DLQ メッセージ > 100 件。

### 1.11 削除/取消/シンク解除

- Google 側で `status=cancelled` または削除された場合  
  - 対応する TCard(SyncOn) は **TCard(SyncOff) に自動降格**し、  
    期日/時間などの情報は Taesk 内に保持する。  
- 「Googleとシンク」チェックを OFF にした場合  
  - いつでもシンク解除でき、カードは TCard として残る。  
  - 再度 ON にすると、近似マッチ候補 UI を経て再シンク可能。

## 3. 受け入れ基準（抜粋）

- 双方向同期  
  - Taesk 編集 → Google  
  - Google 編集 → Taesk  
  - 上記の反映が Push 経路で **p95(E2E) ≤ 60 秒**。

- 競合  
  - `If-Match` 不一致時に再取得し、**新しい側** が採用される。  
  - 自己更新は取り込みでスキップされ、無限ループが発生しない。

- 繰り返し/例外  
  - 例外編集 / 単発キャンセルが正しく展開・反映される。  
  - Taesk 側からの編集は「このインスタンスのみ」として Google に反映される。

- 終日 / 日付だけタスク  
  - 内部的に `date` / `display_tz` / `start_utc` / `end_utc` を持つものについて、  
    DST / TZ 跨ぎでも表示ズレが発生しない。  
  - GCard 終日は Google カレンダーと同等の帯状 UI で表示される。  
  - TCard(SyncOff) / TCard(SyncOn) の「日付だけタスク」は従来通り A/B リスト上のカードとして表示される。  
  - Taesk で「終日」とした TCard(SyncOn) も、Google 側では All-day として表示される。

- エラー表示  
  - 一時的なエラーで TCard(SyncOn) が「同期エラー」バッジになり、  
    正常系に戻ると自動でバッジが外れる。  
  - 認可エラーで権限が完全に失われた場合、TCard(SyncOn) は TCard(SyncOff) に自動降格し、  
    その後は同期されない（再接続が必要）。

## 4. 補足メモ（実装上のポイント）

- GCard は「毎回 Google からライブ取得する」のではなく、**Taesk の DB にキャッシュされたカード**として扱う。  
  - UI は原則 DB を即時表示し、バックグラウンド同期で遅延なく更新されるようにする。  

- `display_tz` は「表示するタイムゾーン」ではなく、**日付をローカル時間としてどのタイムゾーンで解釈するか**を示す。  
  - 表示上のタイムゾーンは、ユーザーのプロファイル設定など別のロジックで選ぶこともあり得る。  
  - 終日イベントについては、`date` + `display_tz` に基づき Google カレンダーと同一の日付範囲になるように実装する。

- 終日 TCard(SyncOn) は、通常の時間指定イベントと同様に A/B テストや機能フラグの対象とする。

## 5. 実装チェックポイント & 確認事項

本章は、「仕様としては決めているが、実装時に意識しておきたいポイント」および  
「共有カレンダーなど、今後深掘りが必要な論点」のメモである。

- **TCard URL 埋め込みの衝突回避（← 1.3）**  
  - 既存説明文との境界を固定する運用だが、ユーザーが説明文を全削除した場合でも、  
    同じ形式で再埋め込みできるようにする（例: `----` 以降を常に Taesk 管理領域とみなす）。

- **近似マッチ候補の UX（← 1.2）**  
  - タイトル Jaro-Winkler 類似度 0.75 以上を候補とする仕様は確定。  
  - ただし候補が 0 件のときの挙動（そのまま新規作成にフォールバックするか、  
    明示的に「新規作成」を選ばせるか）を UI レベルで固定する。

- **近似マッチの検索対象範囲（← 1.2）**  
  - 再シンク時の候補検索を、Taesk DB に保持されている GCard  
    （標準では過去 4 週 / 未来 12 週 + プリフェッチ済み範囲）に限定するか、  
    必要に応じて追加フェッチするかは実装のトレードオフ。  
  - 初期実装としては「DB にある GCard だけを対象」とするのがシンプル。  
- **「シンク解除済み TCard」の判定（← 1.2）**  
  - 過去に Google イベント ID を保持していた履歴（例: `last_google_event_id` など）を基準に、「一度もシンクしていない TCard」と区別する。  

- **終日表示と日付だけタスクのマイグレーション（← 1.5, フェーズ0）**  
  - GCard 終日帯状 UI をフェーズ0で先行するため、既存データ移行（`start/end` だけを持つ G/T レコード）に対して  
    `date` / `display_tz` を補完するマイグレーション手順が必要。  
  - Taesk 側終日帯状タスクは導入せず、A/B リストの「日付だけタスク」を帯状化しない方針は確定。

- **初回フル取得範囲の拡張条件（← 1.4, フェーズ2）**  
  - 基本は過去 4 週 / 未来 12 週だが、ユーザーが「さらに過去を閲覧」した際にどこまで拡張し、  
    再度狭めるか（キャッシュ縮退条件）は実装上のチューニングポイント。  
  - 初期は「ユーザーが表示した範囲はそのまま保持、一定期間アクセスがなければ縮退」のような  
    シンプルなポリシーでよい。

- **display_tz の決定ロジック（← 0.2, 1.5, 4.）**  
  - 「解釈の基準 TZ」として、  
    1. イベントの `start.timeZone`  
    2. カレンダー設定  
    3. ユーザープロファイル設定  
    のような優先順位を実装で固定する。  
- **カレンダーの書き込み権限がない場合の扱い（← 1.9）**  
  - read-only カレンダーでは「Googleとシンク」を無効にするか、押下時に「書き込み権限がありません」と明示して TCard(SyncOff) のままにする方針を決める。  

- **watch 再作成しきい値（← 1.7）**  
  - 「寿命 30% 前」というしきい値はひとまず決め打ち。  
  - 実際のトラフィックや Google の仕様変更などを踏まえて、メトリクスから調整可能にしておく。  
- **自己更新スキップの判定粒度（← 1.6）**  
  - 同一 `event.id` かつ同一 `etag` を自己更新とみなし、`updated` は補助的に扱うなど、優先的に見るキーを固定する。  
- **カレンダー跨ぎ移動時の扱い（← 1.11）**  
  - Google 側でイベントの所属カレンダーが変わった場合、元カレンダーでは「削除」として扱われるため TCard(SyncOn) は TCard(SyncOff) に自動降格する。新しいカレンダーとの再シンクはユーザー操作で行う。  

- **共有カレンダーと複数ユーザーの所有権（← 0.1, 1.7）※要深掘り**  
  - 共有カレンダー上の 1 つの Google イベントを、複数の Taesk ユーザーが閲覧・編集できるケースで、  
    - それぞれが独立した TCard(SyncOn) を持つのか  
    - あるいは「代表」ユーザーの TCard を共有するのか  
  - については、現時点では明示的には決めていない。  
    将来的に共有カードの要件が出た場合は別途仕様化する。

## 6. Google Calendar Sync 仕様と権限についての補足 (2025-12-09 追加)

### 6.1 「再接続候補あり」の判定ロジック
- TaeskはカードとGoogleカレンダーイベントの同期情報を `calendar_sync` テーブルに保存しています。
- 連携解除（Unlink）しても、過去に同期していたGoogleイベントのID（`last_google_event_id`）はDBに残ります。
- UI上の「再接続候補あり」は、「現在は連携していないが、過去の同期履歴（イベントID）がDBに残っている」場合に表示されます。
- これにより、再接続時に「新しい予定」として複製するのではなく、**「元の予定」に対して再同期を試みる**ことができます。

### 6.2 API経由でのイベント説明欄操作
- **基本ルール:** Google Calendar APIであっても、ユーザーがそのイベントに対する**編集権限（書き込み権限）**を持っている必要があります。
  - 自分が主催者のイベント: 当然操作可能。
  - 自分がゲストのイベント: **「ゲストにイベントの変更を許可する」設定になっている場合のみ**操作可能。
- **GCard変換時の挙動:**
  - GCardからTCardへの変換時に説明欄にURLが追加されたということは、その時点で**書き込み権限があった**ことを意味します。
  - したがって、連携解除（Unlink）のAPI操作時も同等の権限があれば、説明欄からURLを削除することが可能です。
- **UIとの違い:**
  - GoogleカレンダーのWeb UI上では、ゲストは自分のカレンダー上のコピー（自分だけのメモなど）しか編集できないように見える場合があります。
  - しかしAPI（およびTaesk）は、権限があれば「イベント本体（全参加者に影響する）」を更新しようとします。変換やUnlinkでの説明欄操作はこれに該当します。
