## 2. アーキテクチャ概要
```
ユーザー操作（コメント投稿 / 返信 / @メンション）
   └─▶ API Routes（`/api/cards/...` / `/api/notifications/...`）で validate → persist
        ├─▶ Supabase DB: comments (mentions uuid[]) / notifications
        ├─▶ Realtime: Comments / Notifications チャネル購読で UI 即時反映
        ├─▶ Sync Queue: オフライン時は既存キューに enqueue → 復帰後に API 実行（Idempotency-Key で重複防止）
        └─▶ 通知生成（@mention, 期限, カード更新）
               ├─▶ アプリ内通知（bell）
               └─▶ Web Push（Service Worker経由）
```

### 2.1 通知チャネル
- **In-App**: ヘッダーのベル、未読数バッジ、通知ドロワー
- **Web Push**: Service Worker + Push API + Notifications API（VAPID/FCM いずれか）
- **Badging（任意）**: PWAアイコンに未読バッジ（対応環境で有効化）

### 2.2 iOS要件（重要）
- iOSでのWeb Pushは**ホーム画面に追加されたPWA**のみ対応
- **ユーザー操作**発火でのみ通知許可を要求（Install → 許可ボタン）

## 3. 仕様詳細

### 3.1 コメント機能
**機能**
- ルートコメント / 返信（`parent_id`）
- 編集・削除（権限: author or editor）
- メンション: `@` でボードメンバーをタイプアヘッド、本文保存時に抽出

**データモデル（確定）**
- ✅ **既存**: `comments.mentions uuid[]` - メンション対象ユーザーのUUID配列
- ✅ **追加**: `create index if not exists idx_comments_mentions_gin on comments using gin(mentions);`
- ❌ **不要**: `comment_mentions` 正規化テーブル（JOINレス運用を継続）
- 既存 API は `mentions` 配列をそのまま返す（変更不要）

**AC（受け入れ基準）**
- [ ] 1秒以内に投稿が反映（楽観更新→確定）
- [ ] 返信が階層構造で表示/折り畳み可能
- [ ] メンションのハイライト/hoverでユーザーカード
- [ ] Realtime購読がカード単位でフィルタされる（他カードの更新で不要な再レンダリングなし）
- [ ] E2E: 新規/編集/削除/返信/メンションが通る

### 3.2 通知の自動生成
**イベント→通知ルール**
- コメント作成 → カード関係者（作成者/アサイニー/参加者）へ通知
- **@メンション** → 対象ユーザーへ必ず通知
- 期限リマインダー（将来） → 締切前N分/時間/日

- **通知タイプ（共通定義）**
  - `'comment_created' | 'comment_replied' | 'mention' | 'assignee_changed' | 'due_soon'`
  - すべての API / 型定義 / Playwright テストでこのセットを使用（小文字スネークケースは禁止）
- **データモデル（確定）**
  - ✅ `notifications` (id, recipient_id, type, payload jsonb, read_at, created_at, dedupe_key text)
  - 未読判定: `read_at IS NULL`
- 📝 **追加予定**: `notification_preferences` (profile_id, in_app_enabled, web_push_enabled, quiet_hours jsonb, updated_at)
  - Phase 3.3 で実装（設定画面と連携）
- 既存の `Notification` 型（`lib/supabase.ts`）との互換性を維持
- 📝 **追加予定**: `notification_preferences` (profile_id, in_app_enabled, web_push_enabled, quiet_hours jsonb, updated_at)
  - Phase 3.3 で実装（設定画面と連携）
- 既存の `Notification` 型（`lib/supabase.ts`）との互換性を維持

- **冪等/重複排除**
  - `dedupe_key = concat_ws(':', type, recipient_id, payload->>'comment_id', payload->>'card_id')`
  - DB 側で UNIQUE 制約を張り、`insert ... on conflict (dedupe_key) do update` を採用
- **AC**
  - [ ] コメント/メンションで未読通知が生成
  - [ ] 既読化でバッジ減算、既読は復元されない
  - [ ] `dedupe_key` により重複通知が登録されない

### 3.3 Web Push
- **クライアント**
  - Service Worker: `public/sw.js`（Next.js `public/` 配下で提供）
  - イベント: `push`, `notificationclick`, `pushsubscriptionchange`
- 購読: `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`
- 許可UX: 明示ボタン（Permission Promptは**ユーザー操作時のみ**）
- 購読情報保存: ✅ 既存テーブル `push_subscriptions` (profile_id, endpoint, p256dh, auth, created_at)

**サーバー**
- 送信: Edge Function（Deno） or API Route で VAPID署名 → Web Push送信
- 冪等: endpoint重複/410 Gone時のクリーンアップ
- レート制御: 1ユーザー/分あたり上限、バッチ配信/リトライ

**AC**
- [ ] Chrome/Edge/Firefox（デスクトップ）で受信
- [ ] Android Chromeで受信
- [ ] iOS 16.4+（PWA）で受信
- [ ] 許可/拒否の状態遷移テスト

### 3.4 Badging（任意）
- インストール済みPWAで `navigator.setAppBadge(count)` により未読数を表示
- 非対応環境では無害にフォールバック

## 6. セキュリティ/パフォーマンス

### 基本対策
- CSRF/XSRF対策、RLS/ACL厳格化
- Rate Limit & バックオフ、重複排除
- 監査ログ（誰に/何件/成功・失敗）

### エラーハンドリング統一
すべての新API/既存API修正は **新式エラーフォーマット** を使用：
```typescript
{ error: { code: string, message: string }, issues?: ValidationIssue[] }
```

**エラーコード例**:
- `VALIDATION_ERROR` - バリデーション失敗（カスタムロジック）
- `INVALID_BODY` - Zod スキーマバリデーション失敗
- `UNAUTHENTICATED` - 未認証
- `FORBIDDEN` - 権限不足
- `NOT_FOUND` - リソース不在

**参考**: `/docs/tickets/2025-10-20/01-unify-error-format-tests.md`
