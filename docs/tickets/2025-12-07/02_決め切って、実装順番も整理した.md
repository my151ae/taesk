# Googleカレンダー連携 v3 — 決定版仕様 & 実装順序
最終更新: 2025-12-07

> 本ドキュメントは「Googleカレンダー連携 v3 設計メモ（改訂版）」を踏まえて、**決め切る**べき仕様を明文化し、**実装順序**まで落としたものです。最後に「未決（A案/B案/推奨）」をまとめています。

---

## 0. 用語とオブジェクト
- **GCard（Googleカレンダーカード）**: Google由来のイベントをTaeskのタイムラインに表示する読み取り主体のカード。編集時に昇格。
- **Linked TCard（Google接続TCard）**: GCardをTaeskで編集した結果、Googleイベントと双方向リンクされたTCard。
- **Unlinked TCard（未接続TCard）**: Google側で削除/キャンセルされた、または接続解除された後にTaeskに残すカード。期日/時間は維持。

状態遷移（要旨）:
- Google → GCard（取り込み）→（編集トリガ）→ Linked TCard
- Google側削除/キャンセル → Unlinked TCard（復接続可能）
- 手動「接続解除」→ Unlinked TCard（復接続候補提示）

## 1. 仕様（決定事項）

### 1.1 データモデル（抜粋）
- 同一性キー: `google_event_id`（第一）/ `recurringEventId`+`originalStartTime`（例外）/ `ical_uid`（再接続候補判断に利用）
- 終日: `is_all_day: bool`, `all_day_dates: {start_date, end_date_exclusive}`, `display_tz`, `start/end_utc`（冗長保持）
- 所有キー: `account_id`, `calendar_id`（将来の複数アカウント/UI切替に備える）
- 監査: `source_etag`, `last_google_sync_at`, `sync_token`, `watch_channel_id`, `watch_expire_at`

### 1.2 取り込み & 同期
- **初回フル取得** → `syncToken`取得 → **差分取得（syncToken）** を基本に、**Push通知（watch）**を主とする。
- **フォールバックポーリング**: Push無更新の異常検知時のみ有効化（頻度は未決セクション参照）。
- **`showDeleted=true`** でキャンセル/削除も検知。`status=cancelled` は Unlinked 化する。
- **410（sync token invalid）**: 透過的フル再同期。UI欠落が出ないようにキャッシュから表示継続。
- **レート制限（429）**: 指数バックオフ（最大待機15分）。

### 1.3 表示/UX（要点）
- 終日（1日/複数日）はヘッダー直下の終日レーンにバー表示。ドラッグで日付移動。
- 参加者とRSVPは**読み取りのみ**表示（5名超は “+n” で省略）。会議URLは表示のみ。
- バッジ: GCard=「Google（未接続）」/ Linked=「Google接続」/ Unlinked=「未接続」/ エラー=「同期エラー」
- 近似再接続候補を未接続ビューで提示（スコア式は未決セクション参照）。

### 1.4 編集・昇格
- GCardを**Taesk側で編集**した時点で Linked TCard に昇格。
- 競合: 更新日時の新しい側を採用（`If-Match`活用）。自動再試行1回、結果トーストで通知。

### 1.5 同期対象フィールド（白リスト）
- **往復同期**: タイトル、説明、場所、開始/終了、終日、会議URL（読み取り主体。`conferenceData`は未編集）
- **Taesk専有（Googleへは書かない）**: ラベル、チェックリスト/サブタスク、担当者、内部コメント、カスタムフィールド

### 1.6 繰り返し & 例外
- `singleEvents=true` で展開。例外は `recurringEventId` + `originalStartTime` を保持し**常に個別インスタンス扱い**。
- 展開ウィンドウは未決セクション参照（実装は可変ウィンドウで対応可能）。

### 1.7 削除/取消/接続解除
- Google側 `status=cancelled` または削除 → Unlinked 化（期日/時間は保持）。
- Taesk側「接続解除」→ 元イベントは残す。再接続は `ical_uid` と時刻近接で候補提示（自動確定しない）。

### 1.8 観測性/SLO
- メトリクス: 取り込み遅延（push/poll）、410/429率、watch再作成失敗率、重複除去率、Unlinked件数、再接続成功率 等。
- SLO例: **p95取り込み遅延 ≤ 60秒**（Push時）、エラー率 ≤ 0.5%。
- アラート例: p95遅延≥60秒が5分継続 / watch残存<30%で未再作成 / DLQ>100 等。

### 1.9 エラーリカバリ
- Push停止検知 → 自動ポーリングON → 復旧確認 → ポーリングOFF（詳細閾値は未決セクション）。
- 例外に備え、全操作は冪等キーで重複排除。

### 1.10 セキュリティ/権限
- **最小スコープ原則**: 既定は `…/calendar.readonly`。編集を行うユーザーはオンボーディングで `…/calendar.events` に同意して昇格。トークン失効時は「再接続」固定導線＋指数バックオフ。

### 1.11 受け入れ基準（抜粋）
- 終日・複数日・DST跨ぎ・異TZ表示でもズレなし。
- 例外編集/単発キャンセルが正しく展開・反映。
- 昇格は“編集操作”でのみ発火（非編集操作では発火しない）。
- 410でフル再同期後もUI欠落なし。Push障害→ポーリング→復旧の一連がメトリクスに可視化。

## 2. 実装順序（依存関係つき）

### フェーズ0: 基盤（1スプリント）
- Google API クライアント/認可（readonly）・データモデル基盤（GCard/Linked/Unlinked/監査）
- 初回フル取得 + 差分（syncToken）/ 410ハンドリング
- タイムライン表示（終日/時刻イベント）・基本バッジ

### フェーズ1: Push & フォールバック（1スプリント）
- watch作成/更新/失効再作成・重複排除
- 異常検知 → ポーリング切替（閾値は仮値で実装し、未決セクションに沿って可変）
- 観測メトリクス/アラートの一次実装

### フェーズ2: 例外/繰り返し（1–2スプリント）
- `singleEvents=true` 展開・例外（`recurringEventId`/`originalStartTime`）
- 展開ウィンドウの可変実装（未決の閾値は設定値で差し替え可能に）

### フェーズ3: 編集/昇格/競合（1–2スプリント）
- GCard編集 → Linked昇格（編集面の保存・差分検出・If-Match）
- 同期対象フィールド白リストの実装
- 競合検出/自動再試行/トースト通知

### フェーズ4: 削除/取消/接続解除（0.5–1スプリント）
- `status=cancelled`/削除のUnlinked化・復接続候補提示
- 手動「接続解除」フロー・復接続ガイド

### フェーズ5: 観測性強化 & SLO（0.5スプリント）
- p95取り込み遅延のSLO監視・ダッシュ整備
- DLQ/失敗再試行可視化・運用Runbook

### フェーズ6: 権限昇格（編集権限の導入）（0.5スプリント）
- `…/calendar.events` への同意導線と段階的ロールアウト
- 失効/拒否のUX（再接続固定導線）

### フェーズ7: 仕上げ（QA/ハードケース）（0.5–1スプリント）
- DST/複数TZ/大規模繰り返し/高負荷での回帰試験
- 文言/バッジ/空状態・エラー状態の磨き込み

> 依存関係: 0 → 1 → 2 → 3/4（並列可一部）→ 5 → 6 → 7

## 3. 未決（A案 / B案 / 推奨・理由）

> 下記は**最終判断のために敢えて残している**論点です。実装はすべて**設定値**で切替可能にし、初期値は「推奨」でデプロイします。

### 3.1 昇格トリガ（GCard→Linked）
- **A案（広め）**: コメント/ピン等の軽操作も昇格対象  
  - メリット: 自然にLinked化され書き戻し漏れが減る  
  - デメリット: 意図せぬ書き戻し、権限昇格が過剰発生
- **B案（狭め）**: タイトル/説明/日時/場所/チェックリスト/カスタムフィールド等、**書き込み意図が明確**な編集のみ  
  - メリット: 事故が少なくUX予測可能  
  - デメリット: Linked化のワンアクションが増える場合がある
- **推奨**: **B案**（狭め）
Linkedは専用チェックボックスでリンクにして、編集したら勝手にLinkedはやめる

### 3.2 同一性/再接続ロジック（候補提示の閾値）
- **A案（自動確定寄り）**: `ical_uid`一致 or 類似度しきい値0.65で自動接続  
  - メリット: 手間が少ない  
  - デメリット: 誤接続リスク／監査の複雑化
- **B案（人手確定）**: タイトル類似（Jaro-Winkler）×0.7 + 時刻近接 e^(-|Δmin|/10)×0.3 ≥ **0.75**で**候補表示のみ**  
  - メリット: 誤接続を抑止、可観測性高い  
  - デメリット: ワンクリック確定の負担
- **推奨**: **B案**（人手確定）
B案なんだけど、Linked専用チェックボックスと繋げたいかな

### 3.3 展開ウィンドウ（`singleEvents=true`）
- **A案（軽量）**: 過去1週 / 未来4週  
  - メリット: 軽い、初期レスポンスが速い  
  - デメリット: 少し先/前の予定が抜けがち
- **B案（広め）**: 過去4週 / 未来12週  
  - メリット: 実用的な見通し、例外の取りこぼし減  
  - デメリット: 取得量増・初回コスト増
- **推奨**: **B案**（広め）
B案で

### 3.4 終日の内部表現
- **A案**: `date`保存 + `display_tz` + `start/end_utc`冗長保持  
  - メリット: DST/TZ跨ぎでの表示一貫性が高い  
  - デメリット: 実装がやや複雑
- **B案**: 00:00–24:00の時刻イベントとしてUTC換算のみ  
  - メリット: 実装が単純  
  - デメリット: DSTでズレる可能性
- **推奨**: **A案**
これってGCard（Googleカレンダーカード）の時だけとすると簡易ではない？
Taeskカードにした時はA/Bリストに入れようと思ったが、ちょっと動きを考えないとかも

### 3.5 同期対象フィールドの範囲
- **A案（広め）**: 参加者/招待・会議情報も編集・往復  
  - メリット: 完全な予定編集体験  
  - デメリット: 仕様/権限/同意の複雑化、失敗点増
- **B案（最小）**: タイトル/説明/場所/開始・終了/終日/会議URL表示主体  
  - メリット: 安定・実装コスト低、責務分離明確  
  - デメリット: カレンダー側での参加者管理が必要
- **推奨**: **B案**（最小）
B案で

### 3.6 Push障害の検知閾値とフェイルオーバ
- **A案（固定）**: 無更新5分でポーリングON（5〜10分間隔）  
  - メリット: わかりやすい  
  - デメリット: 誤検知/過剰ポーリングの可能性
- **B案（動的）**: 「p95取り込み遅延 × 3」を無更新しきい値、ポーリング周期はp95に連動  
  - メリット: トラフィック/遅延に適応、無駄が少ない  
  - デメリット: 実装・監視がやや複雑
- **推奨**: **B案**（動的）
B案で

### 3.7 権限スコープの運用
- **A案**: すべてのユーザーで `…/calendar.events` を最初から要求  
  - メリット: 昇格時の摩擦ゼロ  
  - デメリット: 過剰権限・コンプライアンス懸念
- **B案**: 既定 `…/calendar.readonly`、編集時にオンデマンドで `…/calendar.events` 同意  
  - メリット: 最小特権、安心感  
  - デメリット: 初回編集時に1ステップ増
- **推奨**: **B案**
A案で

### 3.8 Unlinked 自動アーカイブ
- **A案**: 無期限保持（ユーザー任せ）  
  - メリット: データ喪失リスク低  
  - デメリット: ストレージ膨張、検索ノイズ
- **B案**: ボード上限（例: 2,000件）超過で**古い順に自動アーカイブ**＋通知  
  - メリット: パフォーマンス一定、UX維持  
  - デメリット: ポリシー説明/復元UIが必要
- **推奨**: **B案**（上限＋自動アーカイブ）
A案で

## 付録: APIパラメータ指針（要点）
- 取得: `events.list`（`singleEvents=true`, `showDeleted=true`, `timeMin/timeMax`は展開ウィンドウに応じて）, `syncToken`運用
- Push: `channels.watch` / `channels.stop`、失効30%前で再作成。並走期間は冪等キーで重複排除
- 競合: `If-Match` / `etag`、不一致時は再取得→再試行
- レート: 429/5xxは指数バックオフ、最大待機15分
