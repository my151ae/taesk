## 1. 決定事項（ユーザー回答を反映済み）

### 1.1 リンク方式（GCard/Linked/Unlinked）
- **専用チェックボックスでリンク管理**：カード詳細に「Googleとリンク（Linked）」チェックボックスを設け、**ユーザー明示操作**でリンク/解除を切替。
- **編集時の自動解除**：Linked状態のカードを**編集開始した瞬間に自動でUnlinked**へ移行（＝Googleへの書き戻しは発生しない）。
- **一発反映（任意）**：編集後にスナックバーで「Googleにも反映して再リンク」を提示。選択時のみ、該当イベントへ**明示反映→再リンク**を実行。
> 目的: 誤書き戻しを避ける一方、**必要時のみ明示反映**できる運用に統一。

>> なぜ自動解除？一度Linkしたらそれ以降は相互編集状態にして更新していく

### 1.2 リンク候補の提示（近似マッチとの連動）
- 「Googleとリンク」をONにした際、**近似マッチ候補（人手確定）**を表示。
- スコア式（Jaro-Winkler ×0.7 + 時刻近接 e^(-|Δmin|/10) ×0.3）≥ **0.75** 到達で候補表示、**自動確定はしない**。

### 1.3 展開ウィンドウ（`singleEvents=true`）
- **採用**：**過去4週 / 未来12週** を基本ウィンドウ。タイムライン外参照時は段階的プリフェッチ。

### 1.4 終日の内部表現（GCard）
- **GCard**では **A案**（`date`保存 + `display_tz` + `start/end_utc`冗長保持）を採用。DST/TZ跨ぎの表示崩れを防止。

### 1.5 同期対象フィールド（最小）
- **Taesk↔Google（明示反映時のみ）**：タイトル、説明、場所、開始/終了、終日、会議URL（`conferenceData`自体の編集は対象外）。
- **Taesk専有**：ラベル、チェックリスト/サブタスク、担当者、内部コメント、カスタムフィールド。

### 1.6 Push障害の検知/フェイルオーバ（動的）
- **無更新しきい値 = p95取り込み遅延 × 3**。ポーリング周期はp95に追従。復旧確認後に自動停止。

### 1.7 権限スコープ
- **A案**採用：オンボーディングで**全ユーザーに `…/calendar.events` を要求**（編集・明示反映に備える）。
- 失効時は「再接続」固定導線＋指数バックオフ。

### 1.8 Unlinked の保持期間
- **A案**採用：**無期限保持**（ユーザー任意で整理）。

## 2. 実装順序（更新版）

### フェーズ0: 基盤
- 認可（`…/calendar.events` 採用）、データモデル（GCard/Linked/Unlinked/監査）、初回フル取得→差分（syncToken）/410対応、基本表示/バッジ

### フェーズ1: Push & 動的フォールバック
- watch作成/更新/残存寿命<30%再作成、重複排除、p95連動しきい値によるポーリング切替、一次メトリクス/アラート

### フェーズ2: 繰り返し/例外
- `singleEvents=true` 展開、例外（`recurringEventId`/`originalStartTime`）個別扱い、展開ウィンドウ（過去4週/未来12週）実装

### フェーズ3: リンクUI/編集時の自動解除
- 「Googleとリンク」チェックボックス、編集開始→自動Unlink、編集後スナックバー「Googleにも反映して再リンク」
- 近似マッチ候補（人手確定）ダイアログ連動（スコア閾値0.75）

### フェーズ4: 明示反映（書き戻し）
- 白リスト項目の明示反映（差分検出/If-Match/自動1回再試行/結果トースト）
- 接続解除/再リンクフロー、`status=cancelled`/削除→Unlinked化

### フェーズ5: 観測性強化/SLO
- p95取り込み遅延のSLO、DLQ/失敗再試行の可視化、Runbook

### フェーズ6: QA/仕上げ
- DST/複数TZ/大規模繰り返し/高負荷での回帰、文言/空状態/エラー状態磨き込み

> 依存関係: 0 → 1 → 2 → 3 → 4 → 5 → 6

## 3. 残る未決（この版での“のみ”）

### 3.1 Taeskカード（Unlinked/Linked後のローカル）の終日表現
- **案A**: GCardと同一（`date`保存 + `display_tz` + `start/end_utc`冗長保持）で統一  
  - メリット: 実装/認知が一貫、DST事故を最小化  
  - デメリット: 実装コストは若干重め（ただしGCard実装の再利用可）
- **案B**: UTC換算の00:00–24:00固定（簡易）  
  - メリット: 単純・軽量  
  - デメリット: DST/TZ跨ぎで表示ズレの可能性
- **現状提案**: **案A（統一）**に寄せつつ、パフォーマンス懸念が出るまで案Bは保留。

### 3.2 Linkedの初期値（Google取り込み時）
- **案A**: 既定ON（取り込み直後はLinked）。**編集開始で即Unlinked**（本方針と整合）  
- **案B**: 既定OFF（ユーザーが明示でONにした時のみリンク）  
- **現状提案**: **案A**（既定ON）。Google側の更新は自然に追随し、ユーザーが編集した瞬間だけUnlink。
>> この実装は全然違う、1.1,1.2あたりの実装予定と合わせて

### 3.3 「一発反映」の実行タイミングと導線
- **案A**: 編集保存直後のスナックバーのみ  
- **案B**: 詳細パネルに「今すぐGoogleへ反映」ボタンを常設（編集有無に関わらず）  
- **現状提案**: **案A + B併用**（スナックバーは直後の気づき用、常設ボタンは後追い操作用）
