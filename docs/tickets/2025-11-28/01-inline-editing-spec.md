# カード本文のインライン編集に向けた整理（2025-11-28）

## 目的・前提
- ボード上のカード本文を、クリックで直接編集できるようにし、Notion のようなチェックリスト運用をスムーズにする。
- Today/Tomorrow のタイムラインと A/B リストの両方で同じ本文を扱い、所属変更やリアルタイム更新と競合させない。
- App Router でのハイドレーション崩れを避ける（表示制御は Tailwind のユーティリティクラスで行う）。

## 要求整理（現時点の理解）
- 本文クリックでインライン編集を開始する（既存 CardModal との二重編集が起きないよう制御が必要）。
- Enter で改行し、次の行頭にもチェックボックス（`- [ ] ` 相当）が自動で挿入される挙動を再現したい。
- Tab でインデント、Shift+Tab でアウトデント（リスト階層を持てるようにする）。
- A/B リストではカードごとに「本文の行数」を表示する（空行を数えるかは要確認）。
- タイムラインでは通常表示は省略（行数を圧縮/ellipsis）。クリックして編集時のみ本文を広げ、編集完了後は再び省略表示に戻す。

## 決定した方針
- **本文フォーマット: 方針B（構造化）**  
  - checklist を JSON など構造化して保存し、行ID/階層/チェック状態を保持する。将来の「行→カード切り出し」を想定し、パース揺れを避ける。既存本文は破棄して開始する。
- **入力コンポーネント: 方針B（`textarea` 拡張）**  
  - 行頭への `- [ ]` 自動付与、Tab/Shift+Tab で文字列操作。SSR/IME/Undo/ペーストの安定性を優先。構造化フォーマットと紐付く中間レイヤーで、行データ⇔テキストを相互変換する。
- **保存トリガー: ハイブリッド**  
  - Blur と Cmd/Ctrl+Enter で即保存。さらに無入力1–2秒の debounce 自動保存を併用。Esc はキャンセル。衝突時は楽観更新のロールバックを行いフォーカス維持を優先。
- **タイムラインでの展開: 方針A（その場で拡張）**  
  - 通常は行数制限＋ellipsis、編集開始で同じ位置に高さ拡張。編集中は dnd 無効化し、上限高さ＋内部スクロールで周囲との干渉を抑える。
- **A/B 行数表示: クライアント簡易計算**  
  - 非空行のみカウントしてタイトル付近に表示。リアルタイムで再計算し、保存値は持たない（空行は除外）。意味合いは「チェックリストの実質行数メタ情報」。
- **インデント管理: 方針B（階層レベル保持）**  
  - 各行に level を持ち、保存時にスペースへ変換してAPIに送る。将来の行切り出しに備え、階層データをロスなく維持。

## 詳細仕様（追記）
- **checklist スキーマ（案）**  
  ```ts
  type ChecklistLine = { id: string; level: number; checked: boolean; text: string };
  type Checklist = { version: 1; lines: ChecklistLine[] };
  ```  
  - DBは `jsonb` に保存。version を持ち将来変更に備える。行/文字数の上限はアプリ側で制御（上限値は要決定）。
- **データ移行/旧本文**  
  - 運用データなし前提のため旧本文は全破棄で開始。旧フィールドの共存期間は設けない。
- **CardModal**  
  - タイムラインと同じ checklist JSON を直接編集表示する。共通の `ChecklistEditor`（textarea拡張）を使い回す。
- **キーハンドリング**  
  - Enter: 次行を追加（level/checkedは前行継承、checkedはデフォルト false でも可）。  
  - Shift+Enter: 現状は「行内改行なし」とし、新規行を追加（行内 `\n` は持たない運用）。  
  - Tab/Shift+Tab: level を +1/-1（0未満にしない）。行頭以外でも Tab はインデントに割り当て、フォーカス移動は抑止。  
  - 複数行選択時は先頭行に対して処理する（全行へ適用するかは要確認）。  
  - IME 中の Enter は確定扱いとして行分割しない。`composition` 状態を見て制御。
- **ペースト**  
  - 複数行ペースト時は行分割し、`- [ ]` / `- [x]` を含む行は checked をパースして取り込む。未指定は checked=false として追加（詳細ルールは要確認）。
- **省略表示（タイムライン）**  
  - 通常表示はスロット高さ内に収め、超過分は省略。編集時に同位置で高さを拡張し、内部スクロール。行数上限や先頭表示行数は 3 行程度を目安（正確な値は要決定）。編集中は dnd 無効化。
- **A/B 行数カウント**  
  - 非空行（`text.trim().length > 0`）をカウントし、タイトル横など最小限の位置に表示。checked 行も含める（未完了のみ表示に切替える可能性はメモ）。
- **競合・同期**  
  - useSyncQueue で楽観更新。編集中に他クライアント更新を受信した場合は「編集中はローカル優先で保持し、通知バナーで再読み込み or 上書き選択」とする案（最終確定は要確認）。非編集中はリアルタイムで反映。
- **オフライン**  
  - 既存ポリシーに合わせ、オフライン編集はキューし再接続で送信。衝突時の扱いは競合ポリシーに従う（要確認）。
- **メトリクス（例）**  
  - `timeline.checklist_edit_started` / `timeline.checklist_saved` / `timeline.checklist_auto_saved` / `timeline.checklist_save_failed`  
  - ペイロード例: `card_id`, `board_id`, `line_count_before/after`, `checked_count_before/after`, `trigger` (`blur|shortcut|auto`).
- **テスト方針（現状メモのみ）**  
  - 追加の Playwright シナリオは当面なし。将来、インライン編集/Tab/Shift+Tab/省略展開/オートセーブを timeline バッチに追加する余地を残す。

## 追加決定事項
- 既存本文データは全削除で問題なし（運用データなし前提）。
- API/DB は checklist JSON フィールドのみを保持し、旧本文フィールドは廃止。
- CardModal も checklist JSON を直接編集する（テキストへの暫定変換は不要）。
- タイムライン省略はスロット高さまで表示、クリックでその場拡張＋内部スクロール。
- A/B 行数表示は最も簡易な配置（タイトル横など）でモバイルも同様に軽量表示。
- 現時点で E2E 追加テストは不要。

## 実装前に潰すべき懸念
- API/型移行の網羅: checklist JSON を唯一の本文とする場合、`lib/supabase.ts` 型、API 入出力、既存コンポーネント/テストが旧 `description` を参照していないかの棚卸しが必要。
- 保存粒度と衝突: 1 行変更でも全 JSON を PUT するなら衝突時に後勝ちになる。部分パッチ API の有無と楽観更新ロールバックの方針を決めないと編集喪失リスクが残る。
- オートセーブ多重送信: Blur + debounce 併用で多重保存が走る恐れ。in-flight 抑止や失敗時のフォーカス維持/再送手順が必要。
- 編集と dnd 排他: `isEditing` のスコープ（カード単位/ボード全体）次第で誤ドラッグが起きる。A/B ⇄ Timeline の所属切替も含めてガード方法を決める。

## 要確認ポイント（方針案）
- 保存APIの粒度
  - 方針A: 全 JSON を保存（実装簡素、衝突時は後勝ち＋ロールバック通知）。
  - 方針B: 行単位パッチ API を用意（衝突耐性向上、API 追加コスト大）。
  - 推奨: 方針A（Notion 風の軽量入力を優先し、まず全量保存で実装速度とシンプルさを確保。衝突はロールバック通知で最低限担保）。
- オートセーブ制御
  - 方針A: in-flight 中は追加保存をスキップし、完了後に未反映差分があれば再送。
  - 方針B: 逐次キューイングして順次送信（連続変更に強いがキュー管理が必要）。
  - 推奨: 方針A（シンプルな状態機械で足り、Notion 風の短時間入力にも十分。キュー管理コストを避ける）。
- DnD 無効化スコープ
  - 方針A: 編集中のカードのみ dnd 無効化。
  - 方針B: 編集開始でボード全体の dnd を無効化（誤ドラッグ防止を優先）。
  - 推奨: 方針A（Notion 風のカード単位インライン編集を阻害しない。A/B ⇄ Timeline の移動は他カードで継続可能）。
- 行数/文字数上限
  - 方針A: クライアント側で行数・文字数を制限（例: 200 行/各行 500 文字）し、DB は緩め。
  - 方針B: DB 側も厳格な CHECK を置く（保存失敗時の UI ハンドリングが必要）。
  - 推奨: 方針A（Notion 風チェックリスト用途ならクライアント制御で十分。将来運用次第で DB に CHECK を追加）。
- 複数行選択時の Tab/Shift+Tab/Enter
  - 方針A: 先頭行のみを対象（実装簡素、直感に反する場合あり）。
  - 方針B: 選択行全体に適用（意図しないインデントが起きるリスク、Undo 依存）。
  - 推奨: 方針B（Notion 風の複数行インデントが自然。Undo が効く前提で操作性を重視）。
- ペースト/サニタイズ
  - 方針A: プレーンテキストのみ許可、`- [ ]` / `- [x]` のみパースし HTML/Markdown 記号は除去。
  - 方針B: Markdown チェックリストのみ許可し、それ以外は一律テキスト化。長文ペースト時の上限エラー表示を入れるか要決定。
  - 推奨: 方針A（XSS リスクを最小化しつつ Notion 風チェックリストは取り込める。挙動が読みやすい）。
- 競合解決（リアルタイム/オフライン復帰）
  - 方針A: 編集中はローカル優先で保持し、バナーで「再読み込み/上書き」を提示。
  - 方針B: 保存時にサーバー版と行IDでマージ（マージロジックの実装コストが高い）。
  - 推奨: 方針A（Notion 風の軽快さを優先し、UI で選択を促すシンプルな衝突解消）。
- A/B 行数表示
  - 方針A: 非空行の総数で固定。
  - 方針B: 未完了行のみを表示（完了済みを除外）。
  - 推奨: 方針A（メタ情報として簡潔で、Notion のチェックリスト残件数と一致しやすい）。
- タイムライン省略表示
  - 方針A: 行数 3 行 or max-height 固定（例: 120px）で ellipsis。クリックで同位置拡張＋内部スクロール。
  - 方針B: デバイス幅に応じて行数を可変にする（レスポンシブ優先、計算が増える）。
  - 推奨: 方針A（決定論的でハイドレーション安全。Notion 風のその場展開と相性が良い）。

## 進め方のメモ
- UI 実装箇所の候補: `app/(board)/_components/timeline/` 配下（タイムライン）、A/B は同ディレクトリのカードコンポーネントを要確認。
- SSR/ハイドレーション安全策: サイズ計測に `window` を使わず、Tailwind クラスで表示切替。編集時の高さは CSS で制御し、初期レンダリングを決定論的に。
- DnD との棲み分け: インライン編集時はドラッグを無効化するガードを置く（`isEditing` フラグを dnd センサーで参照）。
- 保存・ロールバック: useSyncQueue を介した楽観更新 + 失敗時のリトライ/アラート方針を決める。リアルタイム受信時は編集中はスキップ or 衝突解決を定義。
- 検証方針: Playwright は `PW_WORKERS=1` で `npx playwright test --reporter=json` を利用し、新シナリオを timeline バッチに追加する。ログは `test-results/batches/` へ。
